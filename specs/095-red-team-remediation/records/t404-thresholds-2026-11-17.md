# Spec 095 Stage 4 — T404 audit thresholds (fixed before the run)

Filed 2026-11-17, before any audit execution. These thresholds are
the pre-fixed bars C095-13 requires ("the package's scores are stated
against thresholds fixed before the run"). They are not adjusted
after the run; the stage record scores the run against them as
written here.

## The instance under audit

- A scratch instance of the current build: this stage's clone tree
  (base `cf7fac12`, the Spec 095 Stage 3 merge) copied to an audit
  instance directory on the mini-server, backend served on
  127.0.0.1:8417 with `GLOSSA_API_AUTH=off`, using the copy's own
  stores. No live store is read or written; the live origin is not
  touched. The frontend under audit is the committed `frontend/dist`
  of the base commit (this stage changes no frontend source).
- Read-only live legs for protocol steps 1–2 context only: the
  public tracker page and the hosted application's sign-in screen,
  loaded and screenshotted, nothing submitted.

## Functional checklist (the RT-19 list, 15 items)

1. Create, open, update, delete a project.
2. Create, open, update, delete an experiment.
3. Upload and inspect a corpus.
4. Run an experiment.
5. Cancel a running experiment.
6. Resume an interrupted job.
7. Recover after a backend restart (state intact).
8. Generate a report.
9. Validate export formats offered by the surfaces used.
10. Concurrent work (two jobs at once).
11. Long-running experiment handling (progress visible, no timeout
    failure at the surface).
12. Malformed input and extreme data sizes refused or handled
    without a crash.
13. Database migration and rollback.
14. Application state survives a browser refresh.
15. The served frontend bundle matches its source commit (build
    stamp / asset identity read from the served surface).

Thresholds:

- **F1 (coverage):** at least 12 of the 15 items attempted, where
  "attempted" means executed against the instance or directly
  inspected with filed evidence. Every non-attempted item is named
  with its reason.
- **F2 (outcome):** at least 75% of attempted items PASS. Every FAIL
  is filed with its evidence (screenshot for UI legs, log or response
  excerpt for API legs).

## The eight-step new-researcher protocol (C095-13's steps of record)

1. Arrive from the public page.
2. Establish what the system claims and does not claim.
3. Find one inscription and its evidence trail.
4. Distinguish observation, transcription, hypothesis and claim.
5. Reproduce one published result.
6. Submit one candidate with a falsifier.
7. Follow its adjudication.
8. Export the audit trail.

The driver acts as a new researcher: it uses only what the surfaces
themselves present (no developer documentation, no source code).

- **P1:** at least 6 of the 8 steps completable end-to-end. Every
  step that cannot be completed is filed as a failure with its
  screenshot, at the point of failure.

## Accessibility pass

Over the surfaces the protocol touches (home, signs/inscriptions,
claims, experiment builder, evidence, settings):

- **A1:** zero axe-core violations of severity "critical".
- **A2:** at most 3 axe-core violations of severity "serious", each
  named; and the primary navigation of the home surface is
  traversable by keyboard alone.

If axe-core cannot be executed in the audit environment, the pass is
scored by the manual checklist named in the driver (image alt text,
form labels, heading order, focus visibility, target sizes) and A1/A2
are judged against that checklist's critical/serious equivalents,
with the substitution stated in the run record. A silent downgrade
is not permitted.

## Package verdict

PASS iff F1, F2, P1, A1 and A2 are all met. Otherwise FAIL, with
each unmet threshold named in the stage record.

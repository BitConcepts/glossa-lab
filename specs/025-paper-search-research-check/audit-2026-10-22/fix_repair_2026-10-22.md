# Fix repair record — literature-registry edits vs frozen pins (2026-10-22)

This dated record corrects the fix commission's own batch-A execution
and two statements made about it. It is appended, not edited into the
earlier records; where those records say something this record
supersedes, this record governs.

## What went wrong

Batch A (PR #334) executed proposals P2, P4, and the literature half
of P8 by editing three literature-registry records in place
(`glossa-indus/literature/documents/`: the Fuls 2023 catalogue, the
Fuls chapter, and the Positional Analysis paper), appending a
`metadata_correction` record to each. **Those three files' bytes are
freeze-pinned whole-file by frozen spec tests:**

- `ancient_writing_and_modern_technologies_51831ac9.json` —
  SHA-256 `92e19e6d…` pinned live by **both** `test_spec055_freeze.py`
  (`LITERATURE_SHA256`) and `test_spec057_freeze.py` (source S-1's
  registry pin).
- `fuls2023_catalog_of_indussigns_searchins_1dbdecdb.json` —
  SHA-256 `bb23e5e9…` pinned live by `test_spec057_freeze.py` (S-2).
- `positional_analysis_of_indus_signs_a2bedc93.json` —
  SHA-256 `9b95174b…` pinned live by `test_spec057_freeze.py` (S-3).

Any byte change to those files fails those tests. The P3 edit (the
Roif record) is **not** affected: no test pins that file whole-file
(the checks run against it in the passing suite runs assert other
facts), so P3's in-place correction stands.

## The failure classification, corrected

PR #334's first CI run failed on exactly this collision
(`test_spec055_freeze.py::test_cited_records_carry_the_design_facts`,
computed `214ec049…` vs pinned `92e19e6d…`). That failure was
reported at the time as a cold-cache transient, by identity with a
failure the audit's PR #331 had hit. **That classification was
wrong.** The #334 failure was the deterministic pin collision above.
The reason some runs passed anyway (PR #334's re-run, PR #335) is
consistent with the backend suite's own regeneration behaviour: the
suite regenerates parts of the claims/literature store in-job (the
Spec 029 regeneration tests), which can restore the pinned bytes
before the freeze tests read them; the backend job also runs with
`--maxfail=1`, so only the first failing test is ever reported, and
in the failing runs the Spec 057 test never executed. The flip was
not isolated to a single mechanism, and this record does not pretend
otherwise — what is certain is the pin collision itself, verified
from the test sources and the file hashes. PR #336 (batch C) failed
twice on the same assertion, on a tree whose only relevant content
was batch A's edit — which is what forced the correct diagnosis.

## The repair (lands with batch C, PR #336)

1. **The three literature records are restored byte-for-byte** to
   their pre-batch-A content. Verified after restoration:
   `92e19e6def7eccb42ba0e9f53f5ef3bf9dbb0b9717aa3d675cecb971f5ab0e5c`,
   `bb23e5e9f90c30ebebb2d45e2967fb668a54432a56692a8772753fd228316f47`,
   `9b95174bad62c9a4879ae3db28a03ee52bc665df4e1d9897e65f84f353baa53c`
   — each equal to its frozen pin.
2. **The corrections themselves are preserved, moved to where the
   record rules allow them:** each affected claims dossier now
   carries a dated top-level `audit_correction_2026_10_22` note
   stating the correct source facts and that the registry record is
   freeze-pinned and superseded by the note (P2 on the fuls2023
   dossier, P4 on the ancient-writing dossier, P8's identification on
   the positional dossier). This is the proposals' own alternative
   limb — P2's text reads "correct the intake metadata field, **or
   append a dated note if the field is frozen by convention**"; the
   fields are frozen, so the note route is the execution. The claims
   files' live whole-file hashes are, by the freeze tests' own
   design, not asserted (the stores are regenerated by the suite;
   the tests assert claim facts, which the notes do not touch —
   verified field-by-field before landing).
3. Nothing else in batch A changes: the claim-level notes (P1, P5,
   P6, P7, P8) stand, and P3's registry edit stands.

## What this does not do

It does not re-pin any frozen test to new bytes — that would be a
freeze-fence change, which under the program's precedents needs an
owner ruling, and it is not needed: the corrections are fully on the
record via the dossier notes. If the owner prefers the registry
records themselves corrected, the ruling needed is precisely:
*amend the Spec 055/057 freeze pins for the three literature records
to the corrected bytes*. Until such a ruling, the registry fields
(`detected_year` 2008 on the catalogue, the misattributed DOI on the
chapter, the missing author on the 2013 paper) stand as intake
output, superseded on the record by the dossier notes.

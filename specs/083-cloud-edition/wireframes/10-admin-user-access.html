Annotation — wireframe 10 · not part of the UI
Purpose
Per-user workspace access: from Admin · Users, open one person and see — and edit — their role in every workspace in one grid, with the effective result of each grant stated in plain words beside the control.
Primary action
Changing a row’s role control and pressing “Save changes”.
Changed & why
New surface for the workspace amendment: wireframe 04’s “Manage” note promised per-program membership editing; this is that editing surface, re-pointed at workspaces. Two specimens carry the rules in the UI itself: the Member specimen (j-mensah) shows three different stored outcomes — Member, Viewer, No access — across three workspaces, proving access is per-workspace, not per-person; the Guest specimen (guest-reader) renders the Guest ceiling as a visible note with the Member / Admin / Owner options disabled in the control, so the limit is seen before it can be hit, not reported after a failed save.
Spec claims
C083-19 (the matrix shows exactly the stored grants — the role control and the effective-result column are the same stored grant, and edits take effect on the target’s next request, stated in the lede), C083-17 (per-workspace roles — one person holds different roles in different workspaces, and a Guest’s global type caps every row at Viewer).

# Leg C Governance GAPS — 2026-10-29

Open governance items from the Leg C comprehensive red team (full
findings: hardening program record `legC-findings.md`, 2026-10-29).
Each entry names the finding, why it was not closed by a code fix in
the Leg C hardening PRs, and the accountable owner (role). A GAPS
entry is closed by linking the spec amendment or PR that resolves
it, in the closing entry's ledger note.

## GAP-C01 — No authentication layer (from C-01, Critical)

The backend exposes its full operation surface (terminal, staging
approve/verify/promote, uploads, URL import, environment controls,
priority-register unseal) with no authentication; the only current
mitigation is the default 127.0.0.1 bind. Choosing and building an
auth model (identities, roles, separation of duties for staging
approval vs. promotion) is an architecture decision above a
hardening PR's scope, and Specs 079/080 (supervised/desktop
hosting) raise the exposure it governs.

- **Owner:** program owner (architecture decision), then backend
  maintainer (implementation spec).
- **Interim mitigations shipped by Leg C:** sandbox confinement
  (C-02), intake guards (C-05/C-06), resolvable promotion evidence
  (C-03).

## GAP-C07 — Lifecycle state machine is not storage-enforced (from C-07, High)

`claim_stage.transition_stage` / `claim_bundle.gated_transition_stage`
are sound, but no API endpoint or file writer is forced through
them: claim/anchor records are plain JSON and other writers set
`stage` / `review_status` / `confidence` directly. Closing this
means routing every writer through the gated transitions (or adding
storage-layer validation) — a cross-cutting change that needs its
own spec so each writer's legitimate transitions are enumerated
rather than guessed.

- **Owner:** backend maintainer (spec + implementation).
- **Related shipped mitigation:** the promotion path's evidence
  gate was hardened in C-03; the remaining exposure is direct
  writers other than `/staging/promote`.

## GAP-C13 — Falsifier coverage ambiguity (from C-13, Medium)

Mechanical scan (specs 001–081, 072 excluded by owner order): 762
claims across 51 specs with `claims.json`, 0 without falsifier
text; but 31 specs have no `claims.json` at all and 27 specs'
`spec.md` never mentions a falsifier (002, 004, 013–017, 020–023,
025, 026, 030, 032, 035–041, 043, 066, 079, 080). Many are
infra/validation specs; the register cannot currently distinguish
"no governed claims" from "governed claims with no falsifier".
Each listed spec needs a one-line disposition (no-claims /
claims-elsewhere / falsifier-required) recorded against it.

- **Owner:** spec authors for their specs; program owner for the
  disposition sweep and any constitution-level rule that a spec
  must declare which case it is.

## GAP-C12 — Legacy chi-squared threshold (from C-12, Medium)

`experiment_graph_phase20.py:_chi_squared` declares significance by
`chi2 > 3.84 * max(1, dof)`, a statistically wrong threshold
scaling, in a still-registered graph module. Whether any live
verdict flows through it is untested; the v2 checkers
(`phonotactics_v2`, `site_stats_v2`) were re-run by Leg C and can
fail correctly. Disposition requires the experiment-graph owner to
either retire the legacy module or replace the rule with proper
per-dof critical values, after tracing its live callers.

- **Owner:** experiment-graph maintainer.

## GAP-C09F — Frontend error reporting is fire-and-forget (from C-09, frontend half)

`frontend/src/main.tsx:feLog()` sends with
`fetch(...).catch(()=>{})`: a failed send is invisible in the
browser, and only string/Error `console.error` args are forwarded.
The backend half (unconditional `{"ok": "logged"}`) was fixed by
Leg C; the frontend half belongs to the frontend build owner.

- **Owner:** Spec 081 Phase 2 frontend build owner.

## GAP-ENV — Production runtime venv below the declared engine pin (from C-04 context, Low)

The venv serving the production backend carries AEE 1.0.4 while the
repo pins `applied-epistemic-engineering>=1.5.0,<1.6`; a conforming
venv (AEE 1.5.0) exists on the host. Production can therefore assess
with an older engine than CI. Aligning the served runtime to the
pin (or recording a deliberate exception) is an operations action
tied to the desktop cutover, not a repo change.

- **Owner:** operations / cutover owner.
